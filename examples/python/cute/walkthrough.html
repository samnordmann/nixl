NIXL from a CuTe kernel

The question is small: can a CuTe kernel call NIXL's device API, and can we compose those calls into understandable MoE communication? This prototype answers it with three operations and two programs. It is not a production runtime.

The entire integration

CuTe kernel→three private wrappers→NIXL device API→UCX

nixl_cute.py declares CuTe external functions. device.cu implements them with nixlPut, nixlAtomicAdd, and a system-acquire counter load. build.py compiles that small translation unit into LLVM bitcode, which CuTe links into the kernel.

We still need matching function signatures for the compiler. We do not promise a stable ABI: there is no ABI version, compatibility matrix, manifest, wheel integration, or automatic artifact selection. Rebuild the shims together with NIXL and UCX.

Host setup uses NIXL's existing register_memory, get_xfer_descs, get_remote_descs, and prep_mem_view. Their opaque integer handles become Uint64 kernel arguments. No new owning-handle class is introduced. The application explicitly keeps the original resources alive.

This example uses one GPU thread per device call. It establishes the integration and ordering model, not a throughput target. An optimized warp/persistent implementation is a later, separate review.

Before running

Use separate GPUs on one node, NIXL built from this checkout with UCX GPU-device support, CUTLASS DSL 4.5.1, and LLVM 20. Use the same UCX installation for the host library and the device shims. On CUDA 13, use a separately qualified CUDA-13-compatible CuTe source environment.

# From the repository root, after building/installing NIXL:
export PYTHONPATH="$PWD/src/bindings/python/nixl-meta:$PYTHONPATH"
python examples/python/cute/build.py --ucx /opt/hpcx/ucx --arch sm_100

sm_100 is the GB200 target; choose the actual GPU architecture. Rebuild device.bc after changing it or the headers/toolchain. Use an external job timeout: this prototype does not recover a device waiting on a lost peer.

The launcher creates one process per GPU. Gloo exchanges only CPU metadata, route records, and barriers. The GPU activation and result transfers below are NIXL operations issued from CuTe.

1. Copy a registered GPU buffer

torchrun --standalone --nproc-per-node=2 examples/python/cute/put.py

Each rank allocates send and receive slabs, registers them, exchanges addresses plus NIXL metadata, and prepares a local send view and a remote receive view. Both ranks then copy to the other.

# Inside a one-thread CuTe kernel:
status[0] = ops.put(local_view, remote_view, byte_count,
                    source_byte_offset, destination_byte_offset)

The wrapper waits for its request on the GPU; this is not a CPU synchronization call. The teaching harness subsequently drains the stream and uses a host barrier before checking the receive buffer. It repeats with changing values to exercise reuse, rather than merely checking an initially zero buffer.

The only native-header fix preserves UCX's synchronous-completion result. A CUDA-IPC operation can complete immediately without initializing a pending request; treating it as still in progress would poll invalid completion state. See the small native change.

2. Make readiness observable on the GPU

torchrun --standalone --nproc-per-node=2 examples/python/cute/put.py --signal

The remote view has two descriptors: descriptor 0 is the receive slab, descriptor 1 is an array of 64-bit counters, one per source rank. The sender increments its counter only after a successful PUT.

# Sender, same thread and transport channel:
rc = ops.put(local, remote, bytes, src_offset, dst_offset)
if rc == 0:
    ops.signal(remote, source_rank * 8)

# Receiver, before reading the payload:
ops.wait(local_counter_address + source_rank * 8, expected_count)

A system release fence precedes the counter increment; the receiver polls with a system-acquire load. The counter is therefore a publication boundary, not just an integer that happens to change. Expected counts increase across exchanges and membership changes; they are not reset on rejoin.

A ready signal is not a reuse credit. This MVP uses coarse stream drains and all-rank barriers to ensure old receive contents are consumed before the next exchange overwrites them. It intentionally does not implement a GPU credit scheduler.

3. Compose a complete MoE communication round

torchrun --standalone --nproc-per-node=2 examples/python/cute/moe.py

moe.py is separate from the binding. It uses eight tokens per rank, hidden size 128, top-2 routing, two experts per rank, BF16 payloads, and FP32 weighted accumulation. Its CPU router makes the route decisions easy to inspect.

route + pack→NIXL dispatch→expert→NIXL return→weighted combine
records[owner] = [(token, route_slot, expert_id), ...]
send[owner, row] = input[token]
exchange()                         # recv is indexed by original source

send[source, row] = expert(recv[source, row])
exchange()                         # results return in the same row order

output[token] += weight[token, route_slot] * returned[owner, row]

Every source owns a fixed receive segment at every destination. We reserve tokens × top_k rows per source/destination pair and send padded slabs. This wastes bandwidth but removes variable-size allocation, receive reservation, and GPU packing from the first review. Routing records travel through the CPU control plane; only the BF16 payloads use NIXL.

The stand-in expert is x × (expert_id + 1), rounded to BF16. The source multiplies returned values by its original gate weights, sums in FP32, and casts once. A separate CPU golden calculation checks every generation. This validates dispatch/return correspondence; it does not measure a real FFN or grouped GEMM.

Exercise: use the record (token=3, slot=1, expert=5). With two experts per rank, it goes to rank 2. After the return transfer, the original source combines that row into token 3 using weight slot 1; receive row number is not token identity.

4. Change membership without renumbering experts

torchrun --standalone --nproc-per-node=3 examples/python/cute/moe.py \
  --membership '0,1;0,1,2;0,2;0,1,2'

The sequence expands, removes rank 1 while leaving a hole, then rejoins it. Expert IDs always mean rank × 2 + local_expert: rank 2 retains experts 4 and 5 even when rank 1 is absent. The router masks inactive owners before top-k selection.

load joining peers' metadata and stage their device views
drain old GPU work; synchronize the ranks
commit the new active set; release removed views and metadata
run the next dispatch / expert / combine round

All maximum-capacity processes and registered buffers remain alive as standbys. No rank is killed or replaced. The protocol relies on drained phase boundaries, not stale-message recovery, overlapping membership changes, or failure detection. World.membership contains the entire control-plane transition.

Teardown rule: finish kernels, release every local/remote view, synchronize the owners, then deregister memory. A remote view never grants ownership of another process's storage.
